# ECOTE 2026L — Bottom-Up Parser with Backtracking

Final project for the ECOTE course (Warsaw University of Technology, ELKA).
A command-line **bottom-up (shift–reduce) parser with backtracking** for context-free
grammars, written in pure Python. It checks whether each input word belongs to the language
generated by a grammar and, if so, builds the parse tree and the reversed rightmost
derivation. When detailed output is enabled, it also prints the phases of the syntax tree
development, step by step.

The full project documentation (requirements, design, and test cases) is available in
[`final_documentation.pdf`](final_documentation.pdf).

## Features

- Parses words against a context-free grammar using a **shift–reduce** strategy.
- **Backtracking**: undoes reductions and tries alternative reduction paths when a chosen
  path does not lead to a valid parse tree (implemented via recursion, so the Python call
  stack acts as the backtrack stack).
- Builds a **parse forest** incrementally: shifts create terminal leaves, reductions create
  nonterminal nodes, and the final accepted tree is the root of that forest.
- Reports acceptance or rejection per word, together with the final parse tree and the
  **reversed rightmost derivation** as internally assigned production numbers.
- Detailed mode traces every `SHIFT`, `REDUCE`, and `BACKTRACK` step with the current
  working part, frontier, and forest snapshot.
- Grammar validation with precise diagnostics: line number, expected format, and found text.
- No third-party dependencies — Python standard library only.

## Requirements

- Python **3.10+** (uses `dataclass(slots=True)` and builtin generics).

## Usage

```
python3 src/main.py <grammar.txt> <words.txt> <output.txt> [detailed_output]
```

| Argument | Required | Description |
|---|---|---|
| `grammar.txt` | yes | Path to the grammar file. |
| `words.txt` | yes | Path to the words file (input words separated by `$`). |
| `output.txt` | yes | Path to the output file. All results and errors are written here. |
| `detailed_output` | no | `True`/`true` prints the step-by-step parsing trace; any other value (or omitting it) prints only the final results. Default: `true`. |

Exit codes: `0` on success, `1` on error (the formatted error message is written to the
output file if it was opened, otherwise to stdout).

Example:

```
python3 src/main.py tests/grammars/main_recursive.txt tests/words/abba.txt output.txt False
```

## Input formats

### Grammar file

The first line declares the start symbol; every following line defines one rule.
Alternatives are separated by `/`. Nonterminals are single **uppercase** letters; every
other symbol on a right-hand side is a terminal.

```
START S
S -> S A / a
A -> A b S / b
```

Restrictions:

- No ε-productions.
- No cycles (unit cycles such as `S -> S` or `S -> A` / `A -> S` are explicitly detected
  and rejected).
- The start symbol must appear on the left-hand side of at least one production.

### Words file

One or more words composed of grammar terminals, each terminated by the `$` marker
(newlines are ignored). The file must end with `$` and must not contain empty words.

```
abba$baab$
```

## Output

Without detailed output, each word produces an `ACCEPTED` result with its parse tree and
reversed rightmost derivation, or a `REJECTED` message:

```
ACCEPTED

FINAL PARSE TREE

S/1
├── S/2
│   └── a
└── A/3
    ├── A/4
    │   └── b
    ├── b
    └── S/2
        └── a

REVERSED RIGHTMOST DERIVATION

(2,4,2,3,1)
================================================================================
```

With detailed output enabled, each `SHIFT`, `REDUCE`, and `BACKTRACK` step is printed
before the final result:

```
STEP 1
ACTION : SHIFT
SYMBOL : a
WORKING PART : a
FRONTIER : bba
FOREST
[0] a
[1] b
[2] b
[3] a
```

## Error detection

Grammar errors are reported with the offending line, what was expected, and what was found:

```
ERROR: Grammar error at line 2: expected one uppercase nonterminal on the left side, found 's'
```

Detected cases include, among others:

- Empty grammar file; missing or invalid `START` declaration; no productions after `START`.
- Malformed production lines; missing symbols after `->`; empty alternatives after `/`.
- ε-productions; invalid (non-uppercase or multi-symbol) left-hand sides.
- A start symbol that never appears on a left-hand side; unit cycles such as `S -> S`.

Words-file errors are reported with descriptive messages:

```
ERROR: Words file must end with $.
ERROR: Empty words are not supported.
ERROR: Unable to read words file: words.txt (No such file or directory)
```

## Testing

The project ships a functional test suite of 20 cases (accepted words, rejected words, and
malformed grammars/words files) that compares the generated output against the expected
results in `tests/expected/`:

```
python3 tests/test.py
```

The suite prints the result of each test and exits with code `1` if any test fails.

## Project structure

```
src/
├── main.py                  # Entry point and top-level control flow
├── components/
│   ├── input_reader.py      # CLI args, grammar file, words file
│   ├── grammar_manager.py   # Grammar validation and internal grammar model
│   ├── parser_engine.py     # Shift-reduce loop with recursive backtracking
│   ├── forest_builder.py    # Maintains and updates the parse forest
│   ├── output_formatter.py  # Step records and final result formatting
│   ├── output_writer.py     # Writes to the output file and stdout
│   └── error_handler.py     # ParserError formatting and reporting
└── models/                  # Grammar, Node, ParserState, Match, StepRecord...

tests/
├── test.py                  # Functional test runner
├── grammars/                # Test grammars (valid and malformed)
├── words/                   # Test words
└── expected/                # Expected outputs per test case
```

## Assumptions and scope

- The input is already a valid sequence of lexical units; lexical analysis is outside the
  scope of this project (the parser assumes words are sequences of single-character
  grammar symbols).
- Only syntax analysis is performed; semantic analysis, optimization, and code generation
  are out of scope.
- Rejected words are normal parser results, not errors.
